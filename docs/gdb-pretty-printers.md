# GDB pretty printers

`microfmt` ships GDB pretty printers for its concrete sinks, buffers, and
logger, so `print`/`display` show readable values (`microfmt::buffer_sink
written 2 of 64 bytes = "42"`) instead of raw struct dumps of internal
`m_data`/`m_pos`/`m_capacity` fields.

`microfmt::string_view`, `microfmt::span`, `microfmt::array`,
`microfmt::value_ptr`/`value_ref`, `microfmt::checked_value`, and
`microfmt::expected` are aliases of the corresponding `reloco` types (see
`include/microfmt/reloco.hpp`), so they already render correctly under
[reloco's own GDB pretty printers](https://github.com/jplcz/reloco/blob/master/docs/gdb-pretty-printers.md)
-- microfmt does not duplicate printers for them.

The printers live in one place, `tools/gdb/microfmt_printers.py`, and are
usable in three interchangeable ways.

## 1. Source it directly in a running GDB session

```
(gdb) source /path/to/microfmt/tools/gdb/microfmt_printers.py
```

Useful for a one-off debugging session without touching the target binary
or your GDB configuration.

## 2. Auto-load it for a specific binary

Place a `<binary>-gdb.py` file next to your executable (or anywhere on
GDB's auto-load path) containing:

```python
import sys
sys.path.insert(0, "/path/to/microfmt/tools/gdb")
import microfmt_printers
microfmt_printers.register_microfmt_printers()
```

GDB loads this automatically whenever it loads a matching binary (subject
to `auto-load safe-path`, see below).

## 3. Embed it directly into the binary (no external files)

```cpp
#include <microfmt/gdb_printers.hpp>
```

Including this header anywhere in your program (typically once, from the
translation unit containing `main`) embeds the *entire* contents of
`tools/gdb/microfmt_printers.py` into a `.debug_gdb_scripts` ELF/COFF
section via inline assembly, using GDB's ["Python text" section-script
mechanism](https://sourceware.org/gdb/onlinedocs/gdb/dotdebug_005fgdb_005fscripts-section.html).
When GDB loads the resulting binary, it automatically extracts and runs
that exact script, registering the printers -- no `source` command, no
`<binary>-gdb.py` file, and no `sys.path` setup required on the machine
doing the debugging. This is the recommended option for shipping printers
alongside a distributable binary or a project's own test executables.

This header is opt-in only: it is not included by any other microfmt
header, is not part of `tests/compile_all_headers.cpp`'s default
header-compile check, and adds no cost unless you explicitly `#include`
it. It is also deliberately excluded from automated cross-compiler
testing/CI: the `.debug_gdb_scripts` embedding relies on GNU-assembler
inline `asm` syntax that has no equivalent on MSVC (or other compilers
without GNU inline-asm support), so the header guards its body on
`defined(__clang__) || defined(__GNUC__)` and is a silent no-op elsewhere
-- there is nothing portable to verify by including it by default.

`include/microfmt/gdb_printers.hpp` is generated by
`tools/gdb/generate_embedded_header.py` from `microfmt_printers.py` and
should never be hand-edited; regenerate it after changing the printer
script:

```
python3 tools/gdb/generate_embedded_header.py
```

## `auto-load safe-path`

Both option 2 and option 3 are subject to GDB's `auto-load safe-path`
security setting, which by default only trusts scripts from a small set of
system locations. If GDB declines to load the printers, either add the
binary's directory:

```
(gdb) add-auto-load-safe-path /path/to/binary/dir
```

or add it permanently to `~/.gdbinit`. See the [Auto-loading safe
path](https://sourceware.org/gdb/onlinedocs/gdb/Auto_002dloading-safe-path.html)
section of the GDB manual for details.

## Coverage

Printers are registered for: `span_sink`, `buffer_sink<N>`,
`c_string_sink<N>`, `c_string_span_sink`, `counting_sink`,
`iterator_sink<OutputIt>`, `memory_buffer<N>`, and
`log::basic_logger<MaxSinks, MsgBufferCapacity>` (the type behind
`microfmt::log::logger`, showing its name, level, and configured sink
count).

The following types are deliberately **not** covered, because recovering
their data requires calling through a function pointer or an
externally-owned abstract interface rather than reading plain member
fields -- doing that reliably from GDB's Python API is fragile across GDB
versions and unavailable when inspecting a core file, so the default
struct dump is left as-is:

- `microfmt::sink`, the type-erased callback sink (`ctx` + `write_fn`
  function pointer): its "contents" are whatever the opaque callback would
  write, not a value it stores itself.
- `microfmt::format_args`/`format_args_store`, the type-erased argument
  list backing `make_format_args`: printing an argument requires invoking
  its stored format-thunk function pointer.
- `microfmt::sinks::sbuf_sink<SBufT>`: a thin pointer to a caller-provided,
  arbitrary stream-buffer type; its state lives entirely behind `SBufT`'s
  own (non-microfmt) interface.
- `microfmt::null_sink`: stateless, nothing to print beyond the default
  empty-struct dump.

## Regenerating and testing

After editing `tools/gdb/microfmt_printers.py`:

1. Regenerate the embedded header: `python3 tools/gdb/generate_embedded_header.py`.
2. Sanity-check by compiling a small program that exercises the changed
   type, embedding the header, and inspecting it under `gdb` at a
   breakpoint (see the printer script's own module docstring for the three
   loading styles to try).
